# Код-ревью текущей структуры

## Итоговая оценка

Проект уже имеет рабочее разделение на слои:

```text
app/models      — ORM-модели
app/schemas     — Pydantic-схемы
app/api         — JSON API
app/web         — HTML-страницы
app/services    — прикладные сервисы
app/templates   — Jinja-шаблоны
```

Критических причин для срочного большого рефактора нет. Перед структурными правками добавлен набор RBAC/smoke/integration-тестов, чтобы не ломать рабочий функционал при последующем улучшении архитектуры.

## Что выглядит логично

1. Центральная сущность `Task` связывает исполнителя, автора, комментарии, вложения, инциденты, внешние ссылки и уведомления.
2. Справочники `TaskStatus` и `TaskPriority` вынесены отдельно, поэтому жизненный цикл задачи не зашит напрямую в код.
3. Пользователи и роли разделены через `User` и `Role`.
4. Внешние действия вынесены в сервисы:
   - `audit_service`;
   - `storage_service`;
   - `notification_service`.
5. Zabbix-интеграция сохраняет исходный payload, что важно для расследования инцидентов и отчета.
6. Rocket.Chat-уведомления фиксируются в таблице `notifications`, поэтому внешняя ошибка не теряется.

## Что требует аккуратного рефактора после тестов

### 1. Дублирование web-auth helpers

В разных web-модулях повторяются функции:

```text
redirect_to_login
get_user_from_cookie
require_admin
require_manager_or_admin
```

Правильное место для них:

```text
app/web/deps.py
```

Планируемая структура:

```text
require_web_user(request, db)
require_web_roles(request, db, *roles)
require_web_admin(request, db)
redirect_to_login()
```

### 2. Дублирование task business logic между API и Web

Сейчас логика создания, редактирования и проверки доступа к задаче частично повторяется в:

```text
app/api/tasks.py
app/web/task_pages.py
```

Правильное место для общей логики:

```text
app/services/task_service.py
```

Туда следует вынести:

```text
ensure_task_access
get_task_for_user
create_task
update_task
change_task_status
add_comment
apply_task_filters
```

После этого API и Web будут использовать один источник бизнес-правил.

### 3. CSV reports сейчас находятся в pages.py

Экспорт отчетов лучше вынести в отдельный модуль:

```text
app/web/report_pages.py
```

Это отделит dashboard/login/audit от отчетных endpoint-ов.

### 4. Подключение admin user pages

Из-за ограничений инструмента router админки пользователей был подключен через уже зарегистрированный web-router. Функционально это работает, но архитектурно лучше зарегистрировать его напрямую в `app/main.py`:

```python
from app.web.admin_user_pages import router as admin_user_pages_router
app.include_router(admin_user_pages_router)
```

Эту правку безопаснее делать после прохождения тестов.

### 5. Сортировка комментариев

Комментарии уже отображают ФИО автора. Следующим улучшением стоит явно закрепить порядок комментариев по `created_at`, чтобы порядок не зависел от поведения БД.

Варианты:

```text
relationship order_by в модели Task
или явная сортировка при загрузке карточки задачи
```

## Почему большой рефактор отложен

Сейчас проект рабочий. Большой рефактор без тестов повышает риск сломать роли, загрузку файлов, Zabbix-инциденты или web-cookie auth. Поэтому порядок выбран такой:

```text
1. Сначала автоматические тесты.
2. Затем запуск тестов.
3. Затем точечные исправления.
4. Только после этого структурный рефактор.
```

Так проект сохранит работоспособность и при этом постепенно уйдет от признаков сгенерированной пасты.
