# Подробная документация проекта

## 1. Академическое описание

### 1.1. Назначение системы

Разрабатываемая информационная система предназначена для автоматизации процессов взаимодействия между участниками ИТ-подразделения при обработке заявок, задач и инцидентов мониторинга. Система объединяет функции регистрации задач, назначения исполнителей, контроля статусов, ведения комментариев, хранения вложений, обработки событий внешнего мониторинга, формирования уведомлений, ведения журнала аудита и экспорта отчетных данных.

Основная практическая задача системы состоит в том, чтобы обеспечить единый контур обработки ИТ-работ: от возникновения ручной заявки или автоматического события мониторинга до назначения ответственного исполнителя, фиксации хода выполнения и получения отчетной информации. Такой подход снижает риск потери информации, повышает прозрачность работы исполнителей и позволяет восстановить историю действий по каждой задаче.

Система реализована как web-приложение с JSON API. Это позволяет использовать ее одновременно как интерактивный интерфейс для пользователей и как интеграционную точку для внешних сервисов.

### 1.2. Архитектурный подход

Проект построен по многослойной архитектуре. Каждый слой отвечает за отдельную область ответственности:

```text
app/models      — ORM-модели базы данных
app/schemas     — Pydantic-схемы входных и выходных данных
app/api         — REST API endpoint-ы
app/web         — HTML web-интерфейс
app/services    — прикладная бизнес-логика
app/templates   — Jinja2 HTML-шаблоны
app/core        — конфигурация и безопасность
app/db          — подключение к базе данных
app/static      — CSS и статические ресурсы
```

Такое разбиение выбрано для уменьшения связанности кода. Маршрутизаторы не должны содержать значительный объем бизнес-логики; их задача — принять HTTP-запрос, получить текущего пользователя, вызвать соответствующий сервис и вернуть результат. Бизнес-правила, связанные с задачами, вынесены в `app/services/task_service.py`. Сервисный слой используется как web-интерфейсом, так и JSON API, поэтому поведение системы остается единообразным.

### 1.3. Используемые технологии

#### FastAPI

FastAPI используется как основной web-фреймворк. Он отвечает за регистрацию маршрутов, обработку HTTP-запросов, внедрение зависимостей через `Depends`, валидацию входных данных и генерацию JSON-ответов для API. В проекте FastAPI обслуживает две группы интерфейсов:

1. JSON API в модулях `app/api/*`.
2. HTML web-страницы в модулях `app/web/*`.

#### SQLAlchemy

SQLAlchemy используется как ORM-слой для работы с PostgreSQL. ORM-модели описывают таблицы базы данных и связи между ними. Такой подход позволяет работать с объектами Python вместо ручного написания SQL-запросов для каждой операции.

#### PostgreSQL

PostgreSQL используется как основная реляционная база данных. В ней хранятся пользователи, роли, задачи, комментарии, вложения, события мониторинга, уведомления, аудит и справочники.

#### Pydantic

Pydantic используется для описания схем входных и выходных данных API. Например, при создании задачи через API проверяются типы и ограничения полей: длина заголовка, допустимость необязательных полей, структура тела запроса.

#### Jinja2

Jinja2 используется для генерации HTML-страниц. Шаблоны расположены в `app/templates`. Они получают данные из web-маршрутов и формируют пользовательский интерфейс: список задач, карточку задачи, формы создания и редактирования, страницу аудита, список уведомлений, админку пользователей.

#### MinIO

MinIO используется как S3-совместимое объектное хранилище для файловых вложений. В базе данных сохраняются только метаданные файла: имя, размер, MIME-тип, ключ объекта в хранилище. Сам файл хранится во внешнем объектном хранилище.

#### Zabbix webhook

Интеграция с Zabbix реализована через HTTP webhook. Система принимает событие мониторинга, нормализует поля, сохраняет исходный payload, создает задачу-инцидент и формирует уведомление.

#### Rocket.Chat webhook

Rocket.Chat используется как внешний канал уведомлений. Система формирует структурированное сообщение и отправляет его через webhook, если интеграция включена. Даже если отправка отключена, запись уведомления сохраняется со статусом `skipped`, что позволяет отслеживать факт попытки уведомления.

#### Docker Compose

Docker Compose используется для локального развертывания приложения, базы данных и MinIO. Отдельный `docker-compose.test.yml` используется для запуска автоматических тестов в изолированной тестовой PostgreSQL-базе.

#### Pytest

Pytest используется для автоматического тестирования. Тесты проверяют права доступа, поведение web-интерфейса, API задач, Zabbix webhook и CSV-отчеты.

## 2. Структура проекта

### 2.1. Точка входа приложения

Файл `app/main.py` является основной точкой сборки приложения. В нем создается объект `FastAPI`, подключается статическая директория и регистрируются маршрутизаторы.

К приложению подключаются:

```text
app.web.task_pages          — web-страницы задач
app.web.admin_user_pages    — web-админка пользователей
app.web.report_pages        — CSV-отчеты
app.web.pages               — login, dashboard, incidents, audit
app.web.integration_pages   — web-страница уведомлений
app.api.health              — проверка работоспособности
app.api.auth                — API авторизации
app.api.tasks               — API задач
app.api.attachments         — API вложений
app.api.users               — API пользователей
app.api.dictionaries        — справочники
app.api.audit               — аудит
app.api.integrations        — Zabbix webhook
app.api.notifications       — уведомления
```

Порядок подключения web-маршрутов важен: специализированные маршруты задач и админки подключаются раньше общего `pages_router`, чтобы избежать конфликтов путей.

### 2.2. Конфигурация

Файл `app/core/config.py` содержит настройки приложения. Обычно к ним относятся:

```text
APP_NAME
APP_DEBUG
DATABASE_URL
SECRET_KEY
JWT_ALGORITHM
ACCESS_TOKEN_EXPIRE_MINUTES
MINIO_ENDPOINT
MINIO_ACCESS_KEY
MINIO_SECRET_KEY
MINIO_BUCKET
MINIO_SECURE
ZABBIX_WEBHOOK_TOKEN
ROCKETCHAT_ENABLED
ROCKETCHAT_WEBHOOK_URL
```

Настройки читаются из переменных окружения. Это позволяет отделить код приложения от настроек конкретного окружения: локального стенда, тестового запуска или демонстрационной среды.

### 2.3. Подключение к базе данных

Файл `app/db/session.py` создает SQLAlchemy engine и фабрику сессий `SessionLocal`. Функция `get_db()` используется как FastAPI dependency. На каждый запрос создается отдельная сессия базы данных, после завершения запроса она закрывается.

Файл `app/db/base.py` содержит базовый класс `Base`, от которого наследуются все ORM-модели.

## 3. Модель данных

### 3.1. Role

Файл: `app/models/role.py`.

Класс `Role` описывает роль пользователя в системе. Основные поля:

```text
id          — первичный ключ
code        — системный код роли: admin, manager, worker
name        — человекочитаемое название роли
description — описание роли
is_system   — признак системной роли
```

Роль определяет уровень доступа пользователя. В системе используются три основные роли:

```text
admin   — полный доступ, включая управление пользователями
manager — управление задачами, просмотр отчетов и уведомлений
worker  — работа только со своими задачами
```

### 3.2. User

Файл: `app/models/user.py`.

Класс `User` описывает пользователя системы. Основные поля:

```text
id              — первичный ключ
email           — уникальный email
full_name       — ФИО пользователя
hashed_password — bcrypt-хеш пароля
role_id         — ссылка на роль
is_active       — активность учетной записи
created_at      — дата создания
updated_at      — дата обновления
```

Пароль не хранится в открытом виде. В базе сохраняется только bcrypt-хеш.

### 3.3. Task

Файл: `app/models/task.py`.

Класс `Task` является центральной сущностью системы. Через него связываются пользователь, исполнитель, статус, приоритет, комментарии, вложения, события мониторинга, уведомления и аудит.

Основные поля:

```text
id           — первичный ключ
title        — заголовок задачи
description  — описание задачи
creator_id   — автор задачи
assignee_id  — исполнитель
status_id    — текущий статус
priority_id  — приоритет
source_type  — источник задачи: manual или zabbix
deadline     — срок выполнения
created_at   — дата создания
updated_at   — дата последнего обновления
```

Связи:

```text
creator           — пользователь, создавший задачу
assignee          — назначенный исполнитель
status            — статус задачи
priority          — приоритет задачи
comments          — комментарии
attachments       — вложения
monitoring_events — связанные события мониторинга
external_links    — внешние ссылки
notifications     — уведомления
```

### 3.4. TaskStatus

Файл: `app/models/task_status.py`.

Справочник статусов задач. Примеры статусов:

```text
new         — новая задача
in_progress — задача в работе
done        — завершенная задача
```

Статусы вынесены в отдельную таблицу, чтобы жизненный цикл задачи не был жестко зашит в код.

### 3.5. TaskPriority

Файл: `app/models/task_priority.py`.

Справочник приоритетов задач. Примеры:

```text
low      — низкий
medium   — средний
high     — высокий
critical — критический
```

Приоритеты используются для ручных задач, инцидентов мониторинга и визуального выделения задач в интерфейсе.

### 3.6. TaskComment

Файл: `app/models/task_comment.py`.

Комментарий связывается с задачей и автором. Основные поля:

```text
id         — первичный ключ
task_id    — задача
author_id  — автор комментария
text       — текст комментария
created_at — дата создания
```

В интерфейсе комментарии отображаются с ФИО автора, а не с числовым идентификатором пользователя.

### 3.7. Attachment

Файл: `app/models/attachment.py`.

Класс `Attachment` хранит метаданные файла. Сам файл хранится в MinIO. Основные поля:

```text
id             — первичный ключ
task_id        — задача
uploaded_by_id — пользователь, загрузивший файл
file_name      — исходное имя файла
object_key     — ключ объекта в MinIO
content_type   — MIME-тип
size_bytes     — размер файла
created_at     — дата загрузки
```

Такой подход отделяет хранение бинарных данных от реляционной базы.

### 3.8. MonitoringEvent

Файл: `app/models/monitoring_event.py`.

Класс `MonitoringEvent` хранит событие внешней системы мониторинга. В текущей реализации основным источником является Zabbix.

Основные поля:

```text
id                — первичный ключ
task_id           — связанная задача-инцидент
source_system     — источник события
external_event_id — идентификатор события во внешней системе
host              — узел/хост
trigger_name      — название триггера
severity          — уровень критичности
payload           — исходный JSON payload
received_at       — дата получения
resolved_at       — дата закрытия события
status            — статус события
notes             — служебные заметки
```

Поле `payload` важно для трассировки: оно позволяет сохранить исходные данные, полученные от Zabbix, даже если часть полей не используется в бизнес-логике.

### 3.9. Notification

Файл: `app/models/notification.py`.

Класс `Notification` фиксирует попытку отправки уведомления. Основные поля:

```text
id        — первичный ключ
task_id   — связанная задача
channel   — канал уведомления
recipient — получатель
status    — pending, sent, failed, skipped
payload   — тело уведомления
response  — ответ внешней системы
created_at — дата создания
sent_at    — дата отправки
```

Даже если Rocket.Chat отключен, уведомление сохраняется со статусом `skipped`. Это позволяет видеть, что событие было обработано, но отправка во внешний канал сознательно пропущена.

### 3.10. AuditLog

Файл: `app/models/audit_log.py`.

Класс `AuditLog` используется для фиксации значимых действий пользователей и интеграций. Основные поля:

```text
id          — первичный ключ
actor_id    — пользователь, выполнивший действие
entity_type — тип сущности
entity_id   — идентификатор сущности
action      — действие
diff        — изменения
created_at  — дата события аудита
```

Аудит используется при создании задач, обновлении задач, смене статусов, добавлении комментариев, загрузке файлов и управлении пользователями.

## 4. Сервисный слой

### 4.1. Назначение сервисного слоя

Сервисный слой нужен для отделения бизнес-логики от HTTP-маршрутов. HTTP-маршрут должен отвечать за транспортный уровень: получить запрос, извлечь параметры, определить пользователя и вернуть ответ. Логика проверки доступа, создания задачи, обновления задачи, смены статуса и добавления комментария должна находиться в сервисе.

В проекте эта логика вынесена в `app/services/task_service.py`.

### 4.2. task_service.py

Файл `task_service.py` содержит общий набор функций для работы с задачами. Он используется как JSON API, так и HTML web-интерфейсом.

Основные функции:

```text
user_can_manage_tasks(user)
```

Определяет, имеет ли пользователь право управлять задачами. Возвращает `True` для ролей `admin` и `manager`.

```text
require_task_manager(user)
```

Проверяет, может ли пользователь управлять задачами. Если пользователь не является администратором или руководителем, выбрасывается HTTP 403.

```text
get_status_by_code(db, code)
```

Возвращает объект статуса по его системному коду. Если статус не найден, возвращается ошибка 400.

```text
get_priority_by_code(db, code)
```

Возвращает объект приоритета по его системному коду. Если приоритет не найден, возвращается ошибка 400.

```text
get_user_or_none(db, user_id)
```

Проверяет существование активного исполнителя. Если исполнитель не найден или отключен, возвращается ошибка 400.

```text
task_query(db, include_attachments=False)
```

Формирует базовый ORM-запрос к задачам с подгрузкой связанных сущностей: автора, исполнителя, статуса, приоритета и комментариев.

```text
apply_task_scope(query, user)
```

Ограничивает список задач для исполнителя. Пользователь с ролью `worker` видит только задачи, которые он создал или которые назначены ему.

```text
apply_task_filters(...)
```

Применяет фильтры по текстовому поиску, статусу, приоритету, исполнителю, источнику и датам создания.

```text
ensure_task_access(task, current_user)
```

Проверяет доступ пользователя к конкретной задаче. Администратор и руководитель видят все задачи. Исполнитель видит только свои задачи.

```text
get_task_or_404(db, task_id)
```

Получает задачу по идентификатору или возвращает ошибку 404.

```text
get_task_for_user(db, task_id, user)
```

Получает задачу и сразу проверяет доступ пользователя к ней.

```text
list_tasks_for_user(...)
```

Возвращает список задач с учетом роли пользователя и фильтров.

```text
create_task_record(...)
```

Создает задачу, проверяет статус, приоритет и исполнителя, записывает audit log.

```text
update_task_record(...)
```

Обновляет задачу, формирует diff изменений, записывает audit log.

```text
change_task_status_for_user(...)
```

Меняет статус задачи после проверки доступа и записывает audit log.

```text
add_comment_for_user(...)
```

Добавляет комментарий к задаче после проверки доступа и записывает audit log.

## 5. API-слой

### 5.1. app/api/tasks.py

После рефактора файл `app/api/tasks.py` стал тонким маршрутизатором. Он не содержит основную бизнес-логику, а передает работу в `task_service`.

Основные endpoint-ы:

```text
GET /api/v1/tasks
```

Возвращает список задач. Поддерживает фильтры:

```text
q
status_code
priority_code
assignee_id
source_type
created_from
created_to
```

```text
POST /api/v1/tasks
```

Создает задачу. Доступно ролям `admin` и `manager`.

```text
GET /api/v1/tasks/{task_id}
```

Возвращает карточку задачи. Доступ проверяется через `task_service.ensure_task_access`.

```text
PATCH /api/v1/tasks/{task_id}
```

Обновляет задачу. Доступно ролям `admin` и `manager`.

```text
PATCH /api/v1/tasks/{task_id}/status
```

Меняет статус задачи. Исполнитель может менять статус только доступной ему задачи.

```text
POST /api/v1/tasks/{task_id}/comments
```

Добавляет комментарий к задаче.

### 5.2. app/api/attachments.py

Файл отвечает за API вложений. Основные endpoint-ы:

```text
GET /api/v1/tasks/{task_id}/attachments
POST /api/v1/tasks/{task_id}/attachments
GET /api/v1/attachments/{attachment_id}/download
GET /api/v1/attachments/{attachment_id}/open
```

Проверка доступа к задаче теперь также использует `task_service.ensure_task_access`. Это важно, потому что права доступа к задаче и к ее файлам должны быть согласованы.

Endpoint `/open` поддерживает как Bearer-токен, так и cookie `access_token`, потому что browser-ссылка из HTML-интерфейса не отправляет Authorization header.

### 5.3. app/api/integrations.py

Файл отвечает за прием событий Zabbix. Endpoint:

```text
POST /api/v1/integrations/zabbix/webhook
```

Общий процесс:

1. Проверяется Bearer-токен webhook-запроса.
2. Payload нормализуется через Pydantic-схему.
3. Определяется внешний идентификатор события.
4. Проверяется наличие дубля.
5. Создается задача-инцидент.
6. Сохраняется `MonitoringEvent`.
7. Создается запись уведомления Rocket.Chat.

### 5.4. app/api/users.py

Файл отвечает за административный API пользователей:

```text
GET /api/v1/admin/users
POST /api/v1/admin/users
PATCH /api/v1/admin/users/{user_id}
```

Доступ ограничен ролью `admin`.

### 5.5. app/api/notifications.py

Файл предоставляет список уведомлений через API. Используется для контроля попыток отправки сообщений во внешний канал.

## 6. Web-слой

### 6.1. app/web/deps.py

Файл содержит общие зависимости для HTML-страниц:

```text
redirect_to_login
get_user_from_cookie
```

## 8. Авторизация и разграничение доступа

Система использует JWT access token. Для API токен передается через Authorization header:

```text
Authorization: Bearer <token>
```

Для web-интерфейса токен хранится в cookie `access_token`. Cookie помечается как `httponly`, что снижает риск доступа к токену из JavaScript.

Разграничение доступа реализовано на двух уровнях:

1. API-зависимости в `app/api/deps.py`.
2. Web-зависимости в `app/web/deps.py`.

Правила ролей:

```text
admin   — полный доступ, включая пользователей, задачи, отчеты, аудит
manager — задачи, отчеты, аудит, уведомления
worker  — только свои задачи, комментарии и файлы в рамках доступных задач
```

## 9. Интеграция с Zabbix

Zabbix отправляет HTTP webhook в приложение. Payload может содержать разные имена ключей, поэтому схема интеграции допускает альтернативные названия полей и лишние поля.

Примеры поддерживаемых ключей:

```text
event_id / EVENT.ID / eventid
host / HOST.NAME / host.name
trigger / TRIGGER.NAME / trigger.description
severity / TRIGGER.SEVERITY
subject / ALERT.SUBJECT
message / ALERT.MESSAGE
```

После получения события система:

1. Проверяет токен.
2. Нормализует данные.
3. Проверяет дублирование события.
4. Создает задачу с источником `zabbix`.
5. Сохраняет исходный payload в `MonitoringEvent`.
6. Создает уведомление.

Если `event_id` отсутствует, система генерирует стабильный служебный идентификатор на основе содержимого события.

## 10. Интеграция с Rocket.Chat

Rocket.Chat используется как канал уведомлений. Система формирует structured payload, включающий:

```text
alias
emoji
text
attachments
fields
```

Если Rocket.Chat отключен через `ROCKETCHAT_ENABLED=false`, уведомление не отправляется наружу, но запись в базе создается со статусом `skipped`. Это удобно для локальной разработки и тестирования.

## 11. Хранение файлов

Файлы не сохраняются в PostgreSQL. В PostgreSQL хранится только метаинформация, а содержимое файла передается в MinIO.

Преимущества такого подхода:

1. База данных не раздувается бинарными объектами.
2. Файлы можно отдавать потоково.
3. Можно использовать S3-совместимую инфраструктуру.
4. В будущем проще заменить локальный MinIO на внешнее S3-хранилище.

## 12. Аудит

Аудит фиксирует значимые изменения:

```text
create_task
update_task
update_task_status
create_task_comment
upload_attachment
create_user
update_user
```

В поле `diff` сохраняется суть изменения. Например, при смене статуса сохраняется старый и новый статус.

## 13. Тестирование

Автоматические тесты запускаются через отдельный Docker Compose:

```bash
sudo docker compose -f docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
```

Тестовый compose использует отдельную PostgreSQL-базу и не должен изменять рабочие данные.

Покрываются:

```text
RBAC web smoke tests
API задач
Zabbix webhook
CSV reports
проверка отображения автора комментария
запрет доступа к чужим задачам и файлам
```

Текущий тестовый набор после последнего прогона пользователя проходит успешно.

## 14. Пояснения для чайников

### Что это за проект простыми словами

Это внутренняя система для ИТ-отдела. В ней можно создавать задачи, назначать исполнителей, писать комментарии, прикладывать файлы, смотреть инциденты от мониторинга и получать отчеты.

Если говорить совсем просто: это мини-система заявок и инцидентов.

### Кто чем пользуется

Администратор управляет пользователями, смотрит все задачи, отчеты и аудит. Руководитель управляет задачами и смотрит отчеты. Исполнитель видит только свои задачи и работает с ними.

### Что такое FastAPI

FastAPI — это каркас web-приложения. Он принимает запросы от браузера или другой системы и вызывает нужные функции Python.

Например, когда пользователь открывает `/tasks`, FastAPI понимает, что надо вызвать функцию показа списка задач.

### Что такое PostgreSQL

PostgreSQL — это база данных. В ней лежит вся основная информация: пользователи, задачи, комментарии, статусы, инциденты, аудит.

### Что такое SQLAlchemy

SQLAlchemy — это прослойка между Python-кодом и базой данных. Благодаря ей можно писать не чистый SQL, а работать с объектами Python.

Например, `Task` в коде соответствует таблице `tasks` в базе.

### Что такое Jinja2

Jinja2 — это механизм HTML-шаблонов. Он берет данные из Python и вставляет их в HTML-страницу.

Например, список задач из базы превращается в таблицу задач в браузере.

### Что такое MinIO

MinIO — это хранилище файлов. Если пользователь прикладывает файл к задаче, сам файл отправляется в MinIO, а в базе остается только информация: как файл называется, сколько весит и где лежит.

### Что такое Zabbix webhook

Zabbix может сообщить системе: «на сервере проблема». Приложение принимает это сообщение и создает задачу-инцидент.

То есть задача появляется не руками человека, а автоматически от мониторинга.

### Что такое Rocket.Chat webhook

Rocket.Chat webhook нужен, чтобы система могла отправить сообщение в чат. Например: «создана критическая задача по серверу».

Если чат отключен, система всё равно записывает, что уведомление должно было быть создано.

### Зачем нужен audit log

Audit log — это журнал действий. Он отвечает на вопросы:

```text
кто создал задачу;
кто поменял статус;
кто добавил комментарий;
кто загрузил файл;
кто изменил пользователя.
```

Это нужно для прозрачности и разбирательств.

### Почему сделали сервисный слой

Раньше часть логики была в API, часть в web-страницах. Это плохо, потому что можно случайно сделать так, что API работает по одним правилам, а web-интерфейс — по другим.

Теперь основная логика задач вынесена в `task_service.py`. API и web-интерфейс обращаются туда. Это делает систему логичнее.

### Как понять путь задачи в системе

Обычный сценарий такой:

```text
1. Администратор или руководитель создает задачу.
2. Указывает исполнителя, статус, приоритет и срок.
3. Исполнитель открывает свою задачу.
4. Исполнитель добавляет комментарий или файл.
5. Исполнитель меняет статус.
6. Все действия пишутся в audit log.
7. Руководитель может выгрузить CSV-отчет.
```

Если задача пришла от Zabbix:

```text
1. Zabbix отправляет webhook.
2. Система принимает событие.
3. Проверяет, не было ли такого события раньше.
4. Создает задачу-инцидент.
5. Сохраняет исходный payload.
6. Создает уведомление.
7. Задача появляется в интерфейсе.
```
