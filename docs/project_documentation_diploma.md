# Документация проекта для диплома

## 1. Назначение разрабатываемой системы

Разрабатываемая система предназначена для автоматизации взаимодействия сотрудников ИТ-подразделения при обработке задач, заявок и инцидентов мониторинга. Система позволяет регистрировать задачи, назначать исполнителей, отслеживать статусы выполнения, вести комментарии, прикладывать файлы, принимать события внешней системы мониторинга, формировать уведомления и получать отчетные данные.

Основная цель разработки — создать единый программный контур, в котором ручные задачи и автоматические инциденты обрабатываются по общим правилам. Это позволяет повысить прозрачность работы ИТ-подразделения, снизить риск потери информации и обеспечить сохранение истории действий пользователей.

## 2. Общая архитектура

Система реализована как web-приложение на языке Python. В качестве основного web-фреймворка используется FastAPI. Приложение предоставляет два типа интерфейсов:

1. HTML-интерфейс для пользователей.
2. JSON API для программного взаимодействия и интеграций.

Архитектура проекта разделена на несколько логических слоев:

```text
app/models      — модели базы данных
app/schemas     — схемы входных и выходных данных API
app/api         — REST API
app/web         — HTML-страницы
app/services    — бизнес-логика
app/templates   — HTML-шаблоны
app/core        — конфигурация и безопасность
app/db          — подключение к базе данных
```

Такое разделение позволяет уменьшить связанность компонентов. Маршруты API и web-интерфейса отвечают за прием запросов и формирование ответов, а основная прикладная логика вынесена в сервисный слой.

## 3. Используемые технологии

В проекте используются следующие технологии:

```text
Python          — основной язык разработки
FastAPI         — web-фреймворк
SQLAlchemy      — ORM для работы с базой данных
PostgreSQL      — основная реляционная база данных
Pydantic        — валидация входных и выходных данных
Jinja2          — формирование HTML-страниц
MinIO           — объектное хранилище файлов
Docker Compose  — локальное развертывание сервисов
Pytest          — автоматическое тестирование
```

PostgreSQL используется для хранения структурированных данных: пользователей, задач, комментариев, событий мониторинга, уведомлений и аудита. MinIO применяется для хранения файловых вложений. Такой подход позволяет не сохранять бинарные файлы внутри реляционной базы данных, а хранить в ней только метаданные.

## 4. Основные роли пользователей

В системе предусмотрены три основные роли:

```text
admin   — администратор системы
manager — руководитель или ответственный сотрудник
worker  — исполнитель задач
```

Администратор имеет полный доступ к системе, включая управление пользователями. Руководитель может создавать и редактировать задачи, просматривать отчеты, аудит и уведомления. Исполнитель работает только с теми задачами, которые он создал или которые назначены ему.

Разграничение доступа реализовано как на уровне API, так и на уровне HTML-интерфейса. Для web-интерфейса используется cookie с JWT-токеном, для API — Bearer-токен в заголовке Authorization.

## 5. Модель данных

Центральной сущностью системы является задача `Task`. Она связывает автора, исполнителя, статус, приоритет, комментарии, вложения, события мониторинга и уведомления.

Основные сущности базы данных:

```text
Role              — роли пользователей
User              — пользователи системы
Task              — задачи
TaskStatus        — справочник статусов задач
TaskPriority      — справочник приоритетов задач
TaskComment       — комментарии к задачам
Attachment        — файловые вложения
MonitoringEvent   — события мониторинга
Notification      — уведомления
AuditLog          — журнал аудита
```

Задача содержит заголовок, описание, автора, исполнителя, статус, приоритет, срок выполнения и источник создания. Источником может быть ручное создание пользователем или автоматическое событие от Zabbix.

Комментарии позволяют фиксировать ход выполнения задачи. Вложения позволяют прикладывать файлы. Журнал аудита сохраняет значимые действия: создание задачи, изменение задачи, смену статуса, добавление комментария, загрузку файла и управление пользователями.

## 6. Сервисный слой задач

Для уменьшения дублирования кода логика работы с задачами вынесена в файл:

```text
app/services/task_service.py
```

Сервисный слой используется как API, так и web-интерфейсом. В нем реализованы:

```text
проверка прав доступа к задаче;
получение задачи по идентификатору;
фильтрация задач;
создание задачи;
обновление задачи;
смена статуса;
добавление комментария;
проверка статуса, приоритета и исполнителя.
```

Такое решение позволяет избежать ситуации, когда API и web-интерфейс работают по разным правилам. Если изменяется бизнес-логика задач, достаточно изменить ее в одном сервисном модуле.

## 7. Web-интерфейс

Web-интерфейс реализован с использованием Jinja2-шаблонов. Основные страницы системы:

```text
/login                 — вход в систему
/                      — главная страница
/tasks                 — список задач
/tasks/new             — создание задачи
/tasks/{id}            — карточка задачи
/tasks/{id}/edit       — редактирование задачи
/admin/users           — управление пользователями
/incidents             — события мониторинга
/notifications         — уведомления
/audit                 — журнал аудита
/reports/tasks.csv     — экспорт задач
/reports/incidents.csv — экспорт инцидентов
```

Главная страница отображает агрегированную статистику по задачам и последние задачи. Страница списка задач поддерживает фильтрацию по статусу, приоритету, исполнителю и источнику. В карточке задачи отображаются описание, автор, исполнитель, статус, приоритет, срок выполнения, вложения и комментарии.

Доступность элементов интерфейса зависит от роли пользователя. Например, кнопка создания задачи доступна только администратору и руководителю, а страница управления пользователями доступна только администратору.

## 8. REST API

JSON API используется для программного взаимодействия с системой. Основные группы endpoint-ов:

```text
/api/v1/tasks                 — работа с задачами
/api/v1/tasks/{id}/comments   — комментарии к задачам
/api/v1/tasks/{id}/attachments — вложения задач
/api/v1/admin/users           — управление пользователями
/api/v1/integrations/zabbix/webhook — прием событий Zabbix
/api/v1/notifications         — уведомления
/api/v1/audit                 — аудит
```

API задач поддерживает получение списка задач, создание, получение карточки, обновление, смену статуса и добавление комментариев. При каждом обращении проверяется текущий пользователь и его роль.

## 9. Интеграция с Zabbix

Интеграция с Zabbix реализована через HTTP webhook. Zabbix отправляет событие в систему, после чего приложение создает задачу-инцидент.

Обработка события включает следующие этапы:

```text
1. Проверка Bearer-токена webhook-запроса.
2. Нормализация входных полей.
3. Проверка дублирования по event_id.
4. Создание задачи с источником zabbix.
5. Сохранение исходного payload в MonitoringEvent.
6. Создание уведомления.
```

Система поддерживает разные варианты имен полей, например `EVENT.ID`, `HOST.NAME`, `TRIGGER.NAME`, `ALERT.SUBJECT`. Это делает webhook устойчивым к различным настройкам media type в Zabbix.

## 10. Интеграция с Rocket.Chat

Rocket.Chat используется как канал внешних уведомлений. При создании инцидента система формирует структурированное сообщение и отправляет его через webhook, если интеграция включена.

Если интеграция отключена, уведомление не отправляется, но запись сохраняется в таблице `notifications` со статусом `skipped`. Это позволяет тестировать систему без реального Rocket.Chat и при этом видеть, что уведомление было сформировано.

## 11. Работа с файлами

Пользователь может прикреплять файлы к задачам. Файлы хранятся в MinIO, а в PostgreSQL сохраняются только метаданные:

```text
имя файла;
размер;
тип содержимого;
ключ объекта в MinIO;
пользователь, загрузивший файл;
связанная задача.
```

При скачивании файла система проверяет, имеет ли пользователь доступ к задаче. Это предотвращает доступ исполнителя к файлам чужих задач.

## 12. Журнал аудита

Журнал аудита фиксирует значимые действия пользователей. В него записываются:

```text
создание задачи;
обновление задачи;
смена статуса;
добавление комментария;
загрузка файла;
создание пользователя;
обновление пользователя.
```

Для каждого события сохраняются пользователь, тип сущности, идентификатор сущности, действие, изменения и дата. Это позволяет восстановить историю работы с задачами и пользователями.

## 13. Отчеты

В системе реализован экспорт данных в CSV:

```text
/reports/tasks.csv
/reports/incidents.csv
```

Отчет по задачам содержит идентификатор, заголовок, статус, приоритет, источник, автора, исполнителя, срок выполнения и даты создания/обновления. Отчет по инцидентам содержит идентификатор события, внешний event_id, хост, триггер, критичность, статус, связанную задачу и дату получения.

Экспорт доступен только администраторам и руководителям.

## 14. Тестирование

Для проверки работоспособности используется Pytest. Тесты запускаются в отдельной PostgreSQL-базе через `docker-compose.test.yml`, чтобы не изменять рабочие данные.

Команда запуска:

```bash
sudo docker compose -f docker-compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
```

Автоматическими тестами проверяются:

```text
разграничение доступа ролей;
видимость элементов интерфейса;
запрет доступа к чужим задачам и файлам;
создание задач через API;
смена статуса;
добавление комментариев;
обработка Zabbix webhook;
дедупликация событий мониторинга;
доступ к CSV-отчетам.
```

После последнего прогона тестовый набор проходит успешно.

## 15. Развертывание

Для локального запуска используется Docker Compose. Основной compose-файл поднимает:

```text
app    — FastAPI-приложение
db     — PostgreSQL
minio  — объектное хранилище
```

После изменения Python-кода достаточно перезапустить контейнер приложения:

```bash
sudo docker compose restart app
```

Если менялись зависимости или Dockerfile, используется пересборка:

```bash
sudo docker compose up --build -d
```

## 16. Вывод

Разработанная система реализует полный цикл обработки ИТ-задач и инцидентов: от создания задачи или получения события мониторинга до назначения исполнителя, фиксации хода выполнения, хранения вложений, отправки уведомлений и формирования отчетов.

Система имеет разграничение доступа по ролям, журнал аудита, интеграцию с Zabbix и Rocket.Chat, поддержку файлов через MinIO и набор автоматических тестов. Архитектура проекта разделена на модели, схемы, API, web-интерфейс и сервисный слой, что повышает сопровождаемость кода и упрощает дальнейшее развитие системы.
